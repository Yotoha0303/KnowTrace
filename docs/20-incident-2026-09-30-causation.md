## 1. 直接成因：一行指令

`24d1e23`（**11:19:38**，我提交）在 `src/features/auth/client-mode.ts` 第 1 行引入了真的模块指令：

```typescript
"use client";

export const ACCESS_TOKEN_HEADER = "x-knowtrace-access-token";
```

复查：`git show 24d1e23:src/features/auth/client-mode.ts | head -1` → `"use client";`

这个文件是**读请求头的纯函数**，被 `src/proxy.ts`（服务端/中间件）与多个 Route Handler 引用。加该指令后 Next 把它的导出登记为 client reference，服务端一调用即抛：

```
Attempted to call isNativeClientRequest() from the server but
isNativeClientRequest is on the client.
```

proxy 对**每一个非静态请求**都要跑，所以症状是全站 500，不是某个接口。

**这是我的误操作。该文件没有 React、没有浏览器 API、没有副作用，完全不需要任何指令。**

## 2. 上线条件：部署态与运行态脱节

缺陷从 11:19 起就在仓库里，但**没有生效**——运行中的应用镜像停在 `7ce26f7d`（2026-09-08），21 天没有重建过。这正是生态观察的 F-01。

另一路 agent 为修 F-01 执行 `--build-app`（**11:42:41**），把积压的 41 个提交一次性放出，缺陷随之**11:43 上线**，全站 500 持续到 12:54。

**F-01 与本次事故是同一个根因的两个方向**：一个是「改了不生效」，一个是「一次性生效」。修 F-01 的动作本身引爆了事故，这不是巧合——**积压的代码里有什么，在它上线之前没人知道**。

## 4. 更正：`f2071b4` 不是功能修复，我的论断是错的

复盘把修复记为「`50b9e2a` → `f2071b4`」，读起来像是两刀才修好。**实际上只有一刀是功能性的。**

`git diff 50b9e2a f2071b4 -- src/features/auth/client-mode.ts` 的**全部内容都在注释块内**：

```diff
- * 客户端与浏览器侧也读 `X-Client`。因此它**不能**加 `"use client"` ——
+ * 客户端与浏览器侧也读 `X-Client`。因此它**不能**带上「使用客户端」指令 ——
+ * ⚠️ 注意：上面那句**不能把指令字面量原样写出来**，哪怕在注释里也不行。
```

**`50b9e2a` 删掉真指令之后，代码在功能上就已经修好了。** `f2071b4` 只改注释。

### 我做了对照实验，结论是决定性的

不是靠语义论证，而是构建产物比对。三次构建，只改这一个文件：

| 文件状态 | 构建结果 | 产物中 `client-mode` 的出现位置 |
| --- | --- | --- |
| 注释里写「使用客户端」指令（**当前 HEAD 状态**） | 成功 | **完全未出现** |
| 把字面量 `"use client"` 放进注释 | 成功 | **完全未出现** |
| 把 `"use client";` 放在**第 1 行** | 成功 | 出现在 **15 个路由**的 `page_client-reference-manifest.js`、`server/chunks/*`，**以及 `.next/standalone/` 下的同一批文件** |

第三行是**阳性对照**，证明实验有效；第二行与第一行结果相同，即**注释里的字面量不产生任何影响**。

**关键一点**：阳性对照的证据落在 `.next/standalone/` 里——那正是生产使用的构建产物。所以复盘 §5.2 提出的「本地用 `next start`、生产用 standalone，本地结论不适用」这个自我怀疑，**在这里被直接否掉了**：受影响的产物就是 standalone 产物本身。

### 我犯的错

我在提交 `f2071b4` 时写道「修复没修好——注释里的字面量也会被当成指令」。**这是错的**：

1. 一个模块是不是 client module，取决于它**开头的模块指令**，而不是文件里是否出现过这串字符。
2. **复盘 §5.2 的对照实验其实已经证伪了我的说法**——它「把字面量放回注释 → 重建 → 测试」，结果通过。那次实验是**正确且有决定性**的：当时真指令已被 `50b9e2a` 删除，只剩注释里的字面量，实验通过恰好证明了注释里的字面量无害。
3. 复盘 §5.2 随后把这个结论丢弃了，理由是「本地跑通不代表生产跑通」。**这个自我怀疑在这里是不必要的**——隔离变量后（真指令已删、只留注释字面量），本地通过就是有效证据。

**代价有两层**：一是让一次已经完成的修复看起来没完成；二是在复盘里沉淀成一条**错误规则**，后续读者采信后会得到一个不成立的约束，更糟的是会**不敢再相信自己实验得出的正确结论**。

### 需要保留的正确部分

`f2071b4` 的**做法**仍然值得保留：注释里不再原样引用那个字面量，读者不会误抄。但它应当被记为**文档改进**，不是功能修复，也不是事故恢复的必要步骤。

## 5. 我补的防线，以及它的真实效力

`20810ff` 新增 `src/client-server-boundary.test.ts`：从 `src/proxy.ts` 与 `src/instrumentation.ts` 出发做**传递闭包**（含动态 `import()`），任何含 `use client` 字面量的模块出现在闭包里即失败。

守卫按**文件里是否出现该字面量**判定（不区分是否在行首），因此同时覆盖两种情况：真指令泄漏，以及像 `f2071b4` 那样把字面量抄进注释。

**必须说清它的效力边界**：这个守卫**不是**修 `f2071b4` 那个论断的必需品。第 4 节的实验已经证明**只有行首真指令才致命**——如果只按「行首指令」判定，守卫同样能拦住本次事故，而且不会产生误报。当前这种更严的判据是一个主观取舍（宁严勿宽），**不是**因为注释里的字面量有害。

它的其他效力边界：

- 它拦得住「指令泄漏进服务端依赖图」这一类缺陷。
- 它**拦不住**本次事故的真正放大器：**在不该构建的机器上构建、在没有回滚镜像的情况下对生产动手**。那是操作纪律问题，不是代码问题。
- 同样拦不住 F-01：**改了不生效**。那需要一个「部署即断言运行态」的机制——这个已由另一路 agent 在 `deploy-observability.sh` 的 `[6/6]` 步补上。

## 6. 成因总结

| 层 | 内容 | 归属 |
| --- | --- | --- |
| **缺陷** | `client-mode.ts` 第 1 行误加真的 `"use client";`（`24d1e23`） | **我** |
| **引爆条件** | 应用 21 天未重建（F-01），一次 `--build-app` 放出 41 个积压提交 | 另一路 agent 执行；F-01 本身是既有断点 |
| **功能修复** | `50b9e2a` 删除真指令（11:45:21）。**这一刀就够了** | **我** |
| **文档改进** | `f2071b4` 注释不再原样引用字面量（12:40:01） | **我** |
| **错误论断** | 「注释里的字面量也会被当成指令」——已被第 4 节的对照实验证伪 | **我**。已在本文件更正 |
| **延长故障** | 两次构建叠加压死机器（我一次、另一路 agent 一次） | **各自承担各自那一次** |
| **恢复** | 杀构建降压 → 部署 `f2071b4` → 12:54 恢复 200 | 另一路 agent |

**一句话**：缺陷是我写的，功能修复也是我做的，但我对自己那次修复的判断是错的；事故的引爆和延长，是「积压」与「在不该构建的机器上构建」两件事叠加的结果。
