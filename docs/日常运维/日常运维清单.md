# KnowTrace 日常运维清单

## 每次登录服务器后

- 确认当前主机、当前用户和当前目录，避免在错误机器上操作。
- 查看系统运行时间和负载，确认是否存在异常高负载。
- 查看 CPU、内存、Swap 使用情况。
- 查看磁盘容量，重点关注根分区、Docker 数据目录、备份目录和上传目录。
- 查看最近是否有异常登录、SSH 失败尝试或系统重启。

建议命令：

```bash
hostname
whoami
pwd
uptime
free -h
df -h
last -n 10
```

## 文件与目录

- 检查项目目录是否存在异常文件、误删、权限异常或过大的临时文件。
- 检查上传目录是否仍存在，并确认备份范围包含该目录。
- 检查备份目录是否有新增备份、校验文件和过期备份。
- 检查配置文件是否被意外修改，但不要在记录中复制密钥内容。

建议命令：

```bash
ls -la
du -sh *
```

## Docker 与应用容器

- 使用 `docker ps` 查看当前运行容器。
- 检查应用、PostgreSQL、MySQL、Redis、认证服务、Prometheus、Grafana 是否符合预期。
- 检查容器是否频繁重启。
- 查看关键容器最近日志，优先看 error、warn、panic、timeout、connection refused、permission denied。
- 不要随意执行会删除数据卷的命令，例如 `docker compose down -v`。

建议命令：

```bash
docker ps
docker ps -a
docker logs --tail 100 <container>
```

## KnowTrace 业务健康

- 访问登录页，确认页面可打开。
- 使用健康检查接口确认应用存活和数据库可连接。
- 登录后检查核心页面是否可访问。
- 创建或查看一条测试记录，确认数据库读写正常。
- 检查附件或图片读取是否正常。

建议检查项：

- `/api/health/live`
- `/api/health/ready`
- 登录页
- 记录列表
- 记录详情
- 附件读取

## 监控系统

- 优先通过 SSH 本地端口转发访问 Prometheus 和 Grafana，不直接暴露公网端口。
- 检查 Prometheus Targets 是否 UP。
- 检查 Grafana 数据源是否正常。
- 检查核心仪表盘是否有数据。
- 检查是否存在持续 firing 的告警。

建议端口转发：

```bash
ssh -N -L 9090:127.0.0.1:9090 -L 3001:127.0.0.1:3000 <server>
```

常看页面：

- Prometheus Targets
- Prometheus Alerts
- Grafana 数据源
- Grafana KnowTrace 仪表盘
- Blackbox 探测结果

## 日志系统（PLG：Alloy 采集 + Loki + Grafana 查询）

> 2026-10-03 起由 ELK 换成 PLG，**日志栈改为常驻**，不再有"用前启动、用后停止"。
> 原因与实测数据见 `docs/16-stage3-observability.md`。本节按新栈改写。

- Loki 与 Alloy 应**始终在跑**。它们没跑就是真问题（日志会断），不是"没在用"。
- 在 Grafana 里用 LogQL 查询（与 Prometheus 同一界面）：
  `{container=~".+"}`、`{job="caddy"}`、`{job="nginx"}`、`{job="external"}`。
- 确认四路采集都有流（缺哪一路决定了是"全断"还是"只有宿主机日志断"）：

  ```bash
  for j in caddy nginx external; do
    curl -sG 'http://127.0.0.1:3100/loki/api/v1/series' \
      --data-urlencode "match[]={job=\"$j\"}" | head -c 200; echo
  done
  ```

- 保留期 7 天（`limits_config.retention_period`），由 compactor 执行。
- **不要**把 ELK 时代的那套「先查剩余内存 → 再启动 → 用完停止」照搬过来。

建议记录：

- 日志栈内存占用（`docker stats --no-stream`：loki / alloy）
- 磁盘增长（`df -hT /`、`docker exec knowtrace-loki-1 du -sh /loki`）
- 四路采集是否都有流
- 本次查询了哪些日志
- 是否发现错误模式

## 备份与恢复

- 检查最近一次 PostgreSQL 备份是否存在。
- 检查 go-user-system MySQL 备份是否存在。
- 检查上传目录是否纳入备份。
- 检查备份校验值是否生成。
- 定期做隔离恢复验证，不把“有备份文件”当成“可恢复”。

验收标准：

- 备份文件存在。
- SHA-256 校验存在。
- 能在隔离环境恢复。
- 恢复后能完成登录、查看记录、读取附件。

## 安全与访问

- 检查 SSH 是否仍使用密钥登录。
- 检查是否存在异常登录来源。
- 检查 Caddy、Nginx 或反向代理日志中是否有大量异常请求。
- 检查监控、数据库、Redis、MySQL、PostgreSQL 是否没有直接暴露公网。
- 检查默认密码是否已经在生产环境更换。

## 性能与资源

- 观察 CPU、内存、Swap、磁盘和网络。
- 记录高资源进程。
- 对资源较重组件采用按需启动策略。
- 如果内存紧张，优先确认是否由构建进程、数据库、Node.js 或日志积压导致。
  （日志栈 Loki/Alloy 常驻约 140 MiB，**不是**首要嫌疑，见「日志系统」一节。）

## 发布与变更

- 变更前确认当前 Git 版本和未提交修改。
- 变更前确认备份是否可用。
- 发布后检查容器状态、健康接口、登录页、核心读写流程和监控指标。
- 失败时优先保留日志，再回滚。

## 故障记录

每次故障至少记录：

- 时间
- 现象
- 影响范围
- 首次发现方式
- 排查命令
- 关键证据
- 根因或当前推断
- 处理动作
- 验证结果
- 遗留风险
- 后续改进

## 日常频率建议

- 每天：资源、磁盘、容器、健康接口、监控 Targets。
- 每周：备份校验、日志错误模式、证书有效期、异常登录。
- 每月：隔离恢复演练、依赖更新检查、故障记录复盘、文档更新。
