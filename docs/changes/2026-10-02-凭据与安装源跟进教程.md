## 1. 依据：补读教程后发现的四处不一致

2026-10-02 之前**没有系统读过那份 24 节教程**，只零散引用过它的快照文件。
补读后逐节对照（完整对照表见 `KnowTrace-ops/docs/2026-10-02-…就绪核对.md` §10），
其中四处需要动作：

| # | 教程要求 | 新机实际 | 性质 |
| --- | --- | --- | --- |
| 1 | §10 管理员口令 `openssl rand -hex 24`（随机） | **硬编码 `KnowTrace-Workflow@123`** | **安全**：该机公网可访问，而这对凭据写在公开 README 与 `start-all.ps1` 里 |
| 2 | —（老机为空口令） | `POSTGRES_PASSWORD=knowtrace`（**字面量**） | **安全**：老机为 64 字符 |
| 3 | §16 Caddy **官方 apt 仓库** | Ubuntu 的 `caddy` 包（2.6.2） | 一致性：老机 2.11.4 |
| 4 | §8 Docker **官方仓库** | Ubuntu 的 `docker.io` | **无需动作**：与老机实测**完全相同**（`29.1.3-0ubuntu3~24.04.2`） |

**第 1 条的根因值得记下**：教程用的是**学习目录自己的 `配置样例/init-env.sh`**（会随机生成），
而仓库的 `scripts/linux/init-env.sh` 保留固定默认值（为了本机开发方便）。
**两条路径都没有错，错的是把"仓库脚本"当成了"教程的实现"。**

## 2. 改动方案

### 2.1 服务器侧（三项运维操作）

| 动作 | 方法 | 为什么这样做 |
| --- | --- | --- |
| 改管理员口令 | 用旧口令登录 → `PATCH /api/v1/users/me/update/password` → **双向验证**（新口令 200 / 旧口令非 200） | 认证服务提供了这个端点；新口令在**服务器端生成、不下发到我的上下文** |
| 改 `POSTGRES_PASSWORD` | `ALTER USER knowtrace WITH PASSWORD …` → 用**新口令直连验证** → 改 `.env` → 重建 app | 只有 postgres 容器与 app 的 `DATABASE_URL` 读它（`grep` 确认）；备份走 `compose exec pg_dump`，不用它 |
| Caddy 换官方源 | 按教程 §16 加 keyring + `sources.list.d` → `apt install caddy` → `caddy validate` → 重启 | 老机用 2.11.4 + 同一份 Caddyfile，配置兼容性有先例 |

**都留了回滚**：改口令前把旧值存 `/root/.pg-password.rollback`（600）；
换 Caddy 前把 `.deb` 与 Caddyfile 备份到 `/root/knowtrace-ops/backups/before-caddy-official/`。

### 2.2 仓库侧（根因修复，两侧同步）

| 文件 | 改动 |
| --- | --- |
| `scripts/linux/init-env.sh` | 管理员口令**默认随机**（`generate_secret(24)`）；固定值只在 `--use-fixed-admin-credential` 时用 |
| `scripts/init-env.ps1` | 同上（同一判据），避免只改 Linux 造成**新的不一致** |
| `scripts/start-all.ps1` | 不再无条件打印那对固定凭据；按 `.env` 实际值提示 |
| `README.md` / `docs/11-operations.md` | 同步"默认口令"的说法 |

**幂等判据与 `Ensure-Secret` 一致**（空 / `replace` / `your_` 开头才生成），
并**特别保证不会把已存在的 `KnowTrace-Workflow@123` 当成"需要替换"** ——
否则重跑会把已部署环境的已知口令悄悄换掉，运维人员会登不进去。

## 3. 验收（可判定）

| # | 标准 | 怎么证明 |
| --- | --- | --- |
| 1 | 新口令可登录、旧口令失效 | 两个登录请求的 HTTP 码：新 200 / 旧 401 |
| 2 | 改库后数据完好 | `information_schema` 表数与 `captures` 行数不变 |
| 3 | 改 `POSTGRES_PASSWORD` 后 app 正常 | ready 200 + 容器 `healthy` + 重启次数 0 + 日志无鉴权错误 |
| 4 | Caddy 换源后 TLS 与站点正常 | 公网 ready 200 + `ssl_verify_result=0` + 证书有效期可读 |
| 5 | `init-env` 默认随机 | 空口令时生成**随机值且 ≠ `KnowTrace-Workflow@123`**（`generate_secret(24)` = 24 字节 → urlsafe base64 32 字符，192 位熵；与既有三项密钥同一实现） |
| 6 | **`init-env` 幂等**（最关键） | 已有值重跑**不变**；已存在的 `KnowTrace-Workflow@123` 也**不被替换** |
| 7 | 逃生开关有效 | `--use-fixed-admin-credential` + 空 → 得到固定值 |
| 8 | 随机性 | 三次生成的三个值互不相同 |

## 4. 边界

| 不做 | 原因 |
| --- | --- |
| 改 Docker 源 | 【实测】新机老机**包版本完全相同**，无差异可修 |
| 自动关闭密码登录 | 用户声明自行处理（当前是 root + 密码 + 22 端口） |
| 把管理员口令写进仓库 | 必须**永不**入库；只写到服务器 `/root/knowtrace-admin-credential.txt`（600） |
| 撤换现有会话 | 改口令会使该账号全部会话失效（认证后端无会话列表/单设备撤销）——这是**预期行为**，已告知 |

### 5.1 顺带修掉的一处「我自己写的断言误报」

`verify` 阶段新增的 revision 断言把「运行态 714529d vs HEAD ba1b266」判为 **FAIL**。
**但这是误报**：那 5 个提交只改了 `docs/` 与 `scripts/`，**不进应用镜像**。

**这暴露了断言的语义缺陷** —— 它应该断言"运行态是否包含所有**影响应用镜像**的改动"，
而不是"HEAD 是否相等"。09-30 那次事故的本质正是"15 个 `src/` 文件没进镜像"。
已改为：落后但差异只在文档/脚本 → **WARN**；差异涉及 `src`/`package.json`/`Dockerfile`/`drizzle`/
`services`/`compose*` → **FAIL 并列出未部署的文件**。

【实测】改后：当前场景报 WARN 且验收通过；`影响镜像的文件改动数 = 0` 印证判断正确。
