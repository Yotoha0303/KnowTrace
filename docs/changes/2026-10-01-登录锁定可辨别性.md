# 2026-10-01 登录锁定的可辨别性缺陷

| 项 | 值 |
| --- | --- |
| 记录时间 | 2026-10-01（**变动前先写**；结果见第 6 节） |
| 起因 | 用户报告「无论哪个密码都登录不了」 |
| 变动范围 | `src/app/api/v1/auth/login/route.ts`、`src/features/auth/auth-errors.ts`、`src/components/login-form.tsx` |
| 证据纪律 | 【实测】/【依据：文件】/【推断】 |

---

## 0. 先纠正我在诊断中说错的一句

我对用户说：「锁定时密码正确与错误**返回完全一样**」。

**这句是错的。**【实测】两条消息其实不同：

| 情形 | 语义码 | 消息 |
| --- | --- | --- |
| 密码错 | `AUTH_INVALID_CREDENTIALS` | 账号或密码错误。 |
| 被锁定 | `AUTH_LOGIN_RATE_LIMITED` | 登录尝试过于频繁，请稍后再试。 |

`classifyAuthError` 对上游 2008 的翻译是**正确实现的**
（见 `2026-10-01-登录限流容器IP.md`），前端也会显示它。

**所以"无法分辨"这个说法不成立**——但这不代表体验没问题，
真正的缺口是另外三个（第 2 节）。

---

## 1. 用户实际遭遇的完整链路（实测）

```text
14:35:22  POST refresh → 401     旧会话已失效
14:35:23  POST login   → 401     用旧密码（它已被轮换掉）
14:35:26  POST login   → 401
14:35:29  POST login   → 401
14:35:37  POST login   → 401     第 5 次
14:35:39  POST login   → 429     之后全部锁定
14:35:46 / 14:35:48 / 14:35:53 → 429
```

**用户从 14:35:39 起被锁 15 分钟**，期间**即使输入正确密码也返回 429**
（已用探针账号实测复现：前 4 次 401、第 5 次起 429、**正确密码也是 429**）。

**这是限流的正确行为**，不是 bug。问题在于**用户无从预知、也无从理解**。

---

## 2. 真正的三个缺口

### 缺口 A：BFF **完全没接** `Retry-After`【实测】

```
grep "Retry-After" src/app/api/v1/auth/login/route.ts \
     src/features/auth/go-user-system.ts src/features/auth/auth-errors.ts
→ 空
```

上游 `respondLoginRateLimited` **确实设了** `Retry-After` 头（`user_handler.go`），
但 BFF **没有把它读出来、也没有透传**。

**后果**：前端**不知道还要等多久**，只能说一句「请稍后再试」。
用户于是反复重试——**而每次重试都在延长自己的锁**。

### 缺口 B：没有「最后一次尝试」的预警

失败的倒计时是 **5 次**，但前 4 次都只说「账号或密码错误」，
**没有任何提示告诉用户正在逼近上限**。

**后果**：用户正常地「试几个我记得的密码」，第 5 次就撞上锁，
而且撞上时**完全不知道是自己试多了**。

### 缺口 C：锁定文案不说明「被锁」

「登录尝试过于频繁，请稍后再试」读起来像**「慢一点」**，
不像**「你已经不能登了，要等 15 分钟」**。

---

## 3. 改动方案

| # | 改动 | 位置 |
| --- | --- | --- |
| a | **BFF 透传 `Retry-After`**，并在响应体里给出可读的剩余秒数 | `login/route.ts` |
| b | **锁定文案说明它是锁定**，并带上剩余时间 | `auth-errors.ts` |
| c | **前端在锁定时显示倒计时**，而不是一句静态文案 | `login-form.tsx` |
| d | **失败次数接近上限时预警** | 需要把「已失败几次」透出——见第 4 节 |

---

## 4. 关于缺口 B（预警）的一个取舍

要做到「这是最后一次尝试」，BFF 需要知道**当前已失败几次**。
但上游**只在触发限流时才回 `Retry-After`**，前 4 次失败**不返回计数**。

**两条路**：

| 路 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 上游增加「剩余尝试次数」的响应字段 | 改 `services/go-user-system` —— 它是 subtree，改了会与上游分叉 |
| **B** | **不改上游**，本次只做 a/b/c；预警留待将来 | 少一个体验改进，但零分叉风险 |

**本次选 B**：a/b/c 已经能解决「撞上锁却不知道怎么回事」这个主要痛点
（用户至少能看到「已锁定，还需 N 分钟」）。
**不动 subtree** 是项目一贯的纪律（见 `2026-10-01-登录限流容器IP.md` 第 5 节）。

## 6. 执行结果

**填写时间：2026-10-01**（本地验证通过，部署见 6.4）

### 6.1 逐项对照

| # | 改动 | 结果 |
| --- | --- | --- |
| a | BFF 透传 `Retry-After` + 响应体给结构化 `retryAfterSeconds` | ✅ `login/route.ts` |
| b | 锁定文案说明「被锁定」并带剩余时间 | ✅ 「因连续登录失败，登录已被临时锁定。请在约 N 分钟后重试。」 |
| c | 前端显示倒计时 | ✅ 按钮变「已锁定 · Ns」并禁用，每秒递减 |
| d | 失败预警 | ❌ **未做**（理由见计划第 4 节，需改 subtree） |

### 6.2 覆盖链路

```text
go-user-system 设 Retry-After
  → requestGoUserSystem 读出并放进 GoAuthResult.retryAfterSeconds   ← 新增
  → classifyAuthError 用它拼出「已锁定 + 剩余时间」                  ← 新增
  → BFF 透传 Retry-After 头 + 响应体带 retryAfterSeconds             ← 新增
  → login-form 读结构化字段做倒计时，锁定期间禁用提交                 ← 新增
```

**关键**：前端从**结构化字段**取剩余秒数，**不解析文案** ——
文案将来改了不会打断倒计时。

### 6.3 测试与证伪

新增 **2 条**测试，并**证伪过**：

| 测试 | 在**旧代码**上 | 判定 |
| --- | --- | --- |
| 锁定文案含「锁定」与剩余时间 | **失败**（`expected '登录尝试过于频繁，请稍后再试。' to contain '锁定'`） | ✅ **真回归测试** |
| 密码错文案**不得**含「锁定」与时间 | 通过 | ✅ 承重：防止两者被混成一句 |

第二条是**反向断言**——它守的是「不要把两类错误混起来」，
所以它在旧代码上通过是**正确的**（旧代码本来就分得开）。

**验收**：单测 **180 通过**、tsc 0 错、lint 0 error、`next build` 通过。
