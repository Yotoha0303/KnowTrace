## 1. 依据：真机演练暴露的 4 处缺口

2026-10-02 在一台全新 Ubuntu 24.04（1.8 GB / 2 vCPU）上按 `bootstrap.sh` 实际部署，
**`apps`、`monitoring`、`ops` 三个阶段各失败一次**，全绿耗时约 24 分钟。
四处缺口的实测证据：

| # | 缺口 | 实测现象 | 根因 |
| --- | --- | --- | --- |
| 1 | **两个 external 卷不存在** | `docker compose up` 报 `external volume "go-user-system_mysql_data" not found`，**连构建都没开始** | 唯一创建它们的是 `scripts/start-all.ps1`（**PowerShell**），Linux 侧无对应实现 |
| 2 | **`/etc/knowtrace/` 父目录不存在** | `ops` 阶段 `install: cannot create regular file '/etc/knowtrace/ops.conf': No such file or directory`，`set -Eeuo pipefail` 导致**中止，单元一个都没装** | 该目录在老机上是 2026-09-29 手工建的，没有任何脚本创建它 |
| 3 | **nginx 站点文件不存在** | `install-observability-nginx.sh` 报「现有 Nginx 站点不存在」，`exit 1` | 该文件只由仓库提供内容，从不由任何脚本安装 |
| 4 | **Ubuntu 默认站点占 `:80`** | Caddy 与 nginx 的 `default` 抢 80 端口，TLS 无法建立 | 脚本没有处理 `/etc/nginx/sites-enabled/default` |
| 5 | **uploads 属主未修**（隐性） | 修复前实测 `data/uploads` 是 **`root:root`**；不修则图片上传 100% `EACCES`（曾静默 42 次） | `fix-uploads-ownership.sh` **没有任何部署脚本调用**，只在文档的升级步骤里手工执行 |

**这五处都不是"脚本写得差"，而是"编排缺步骤"** —— 每个修复体量都是几行。

## 2. 改动方案

### 2.1 新增 `scripts/linux/prepare-host.sh`（宿主机准备，幂等）

把上述 1、3、4、5 收进一个脚本，**可在 `apps` 之前/之后安全重跑**：

| 动作 | 对应缺口 |
| --- | --- |
| `docker volume create go-user-system_{mysql,redis}_data`（已存在则跳过） | 1 |
| 安装 `deploy/nginx/knowtrace-vps.conf` → `/etc/nginx/sites-available/knowtrace.conf`，并建 `sites-enabled` 软链 | 3 |
| 移除 `/etc/nginx/sites-enabled/default`（先备份到 `/root/knowtrace-ops/backups/`） | 4 |
| 调 `fix-uploads-ownership.sh`（`--fix-uploads` 时才做，因为它要求数据目录已存在） | 5 |

**不包含**（理由见 §4）：UFW、sshd、Caddyfile、apt 装包。

### 2.2 `bootstrap.sh` 加 `host` 阶段

```bash
--stage host    # 调 prepare-host.sh：建卷 + 边缘配置 + （可选）属主修复
```

- `host` 阶段放在 `--all` 的**最前面**：`host → apps → monitoring → ops → verify`
- `apps` 阶段在 `compose up` 之后**自动调用一次属主修复**（缺口 5 的顺序要求：
  `up` 会重建绑定挂载目录，所以必须紧跟在它之后）
- **`host` 与 `apps` 之外不动**：不改变既有阶段语义

### 2.3 `ops` 阶段补 `install -d /etc/knowtrace`（缺口 2）

一行修复，并在 `--dry-run` 里也打印出来。

### 2.4 结束时列出「还需要你做的」（`bootstrap.sh` 的 `b_report_remaining_manual()`）

**实际实现与本节初稿不同**：初稿想在 `lib/common.sh` 加一个通用的
`b_need_root_action()`；实际做成 `bootstrap.sh` 里的 `b_report_remaining_manual()` ——
因为它要读 `BOOTSTRAP_DIR/.env` 与 `systemctl` 状态做**探测**，放在主脚本里更自然，
且不需要改 `common.sh` 的公开接口。

它逐个探测四项并**只列出确实缺的**（已完成的不会刷屏）：

| 探测 | 缺失时打印什么 |
| --- | --- |
| `/etc/caddy/Caddyfile` 是否存在 | 写入提示 + `caddy validate` + 仓库内的模板路径 |
| `systemctl is-active ufw` | **先放行 SSH 端口**的警告（自锁风险）+ 完整命令序列 |
| `.env` 里 `POSTGRES_PASSWORD` 是否还是字面量 `knowtrace` | 提示改它有**丢数据风险**，应在维护窗口做 |
| `/etc/knowtrace/age-recipient.pub` | 提示异地备份会被 `ConditionPathExists` 静默跳过，需先选后端 |

**为什么要有它**：本项目最贵的教训是「部署看起来成功了」——
脚本跑完 ALL GREEN，而实际上 Caddyfile 没有、UFW 没启、口令还是默认值。
与其让这些躺在文档第 4 节里，不如在结束时当面列出来。

### 2.5 `verify` 阶段补 3 项断言

现有只查 3 个端点。补：

- **运行态 revision == HEAD**（09-30 事故的核心判据：`/api/metrics` 里的 `knowtrace_build_info`）
- **uploads 可写**（缺口 5 的显式断言，而不是等用户上传图片才发现）
- **5 个 timer 已 enable**（缺口 2 的直接后果）

## 3. 验收（可判定）

沿用本项目纪律：**「命令返回 0」不算验收，「状态改变」才算**。

| # | 标准 | 怎么证明 |
| --- | --- | --- |
| 1 | `--stage host` 在**没有**两个卷的机器上跑完，`docker volume ls` 出现这两个卷 | `docker volume ls` 前后对比 |
| 2 | 同上，`/etc/nginx/sites-available/knowtrace.conf` 出现且 `nginx -t` 通过 | `nginx -t` 退出 0 **且**文件存在 |
| 3 | `/etc/nginx/sites-enabled/default` 消失 | `[ ! -e ]` |
| 4 | `--stage ops` 在**没有** `/etc/knowtrace` 的机器上跑完，`/etc/knowtrace/ops.conf` 存在（0600）且 3 个 timer enabled | `systemctl is-enabled` × 3 |
| 5 | `--stage verify` 新增的 3 项断言全部 OK | 看输出 |
| 6 | **幂等**：`--stage host` 连跑两次，第二次全部 `[ 跳过 ]` 且无副作用 | 第二次输出无 `install`/`create` |
| 7 | `--dry-run` 下**不改任何东西**，但打印出将要执行的命令 | 跑完后 `docker volume ls` 与文件系统不变 |

**目标结论**：`bootstrap.sh --all` 能在**一台已装好系统依赖、已 clone、DNS 已解析的机器**上
从零跑到全绿 —— 即从「1 条命令 + 5 类人工」收敛到「1 条命令 + 2 类人工（apt 装包、UFW/sshd）」。

## 4. 边界（本次明确不做，以及为什么）

| 不做 | 原因 |
| --- | --- |
| **apt 安装系统包** | 在服务器上执行 `apt-get install` 是写操作；且发行版相关。**建议做成 `--install-deps` 显式开关**，本次先不做，避免"一键"变成"一键改系统" |
| **UFW / sshd 加固** | **自锁风险**：`ufw --force enable` 前未放行 SSH 端口会立即失联且无法远程改回。**永远不该默默执行** |
| **Caddyfile** | 与域名强相关（当前硬编码 `knowtrace.duckdns.org`）。改为从 `--domain` 参数生成，而不是搬一份固定文件 |
| **异地备份 / 告警邮箱** | 需要外部凭据与后端选择，属设计上的人工输入 |
| **改 `deploy-observability.sh` 的 offsite 单元缺失** | 那是另一处缺口（03），影响面不同，单独处理 |
| 动 `compose*.yaml` / `Dockerfile` / `src/` | 本次只碰编排 |

## 5. 回滚

全部改动集中在 `scripts/bootstrap/` 与**新增**的 `scripts/linux/prepare-host.sh`：
- 回滚 = `git revert` 本次提交（无需重建镜像，`bootstrap.sh` 不进镜像）
- `prepare-host.sh` 对系统的改动是**幂等且可列出的**（两个卷、一个 nginx 站点文件、删一个 default 软链）
- 删 default 站点会先备份到 `/root/knowtrace-ops/backups/<时间戳>-default-site/`

## 6. 执行结果（2026-10-02 实测）

**全部改动已在真机（同一台 Ubuntu 24.04）上逐条验证**，含"制造破损 → 验证修复"的破坏性测试。

### 6.1 验收标准逐条对账

| # | 标准 | 结果 |
| --- | --- | --- |
| 1 | `--stage host` 能建出两个卷 | ✅ `[ OK ] 已创建卷：go-user-system_redis_data`（实测复现了缺卷报错 `external volume "go-user-system_redis_data" not found`，随后 host 阶段修好；redis healthy、公网 200） |
| 2 | nginx 站点文件出现且 `nginx -t` 通过 | ✅ 删掉站点配置后重跑 host，`[ OK ] 已安装站点配置` + `[ OK ] nginx -t 通过` |
| 3 | `/etc/nginx/sites-enabled/default` 消失 | ✅ 注入 default 后重跑，`[ OK ] 已移除 default 站点（备份：/root/knowtrace-ops/backups/…-default-site）` |
| 4 | `--stage ops` 在无 `/etc/knowtrace` 的机器上跑完 | ✅ 删除整个目录后重跑：目录重建、`ops.conf` 0600、**3 个巡检 timer 全部 enabled** |
| 5 | verify 新增 3 项断言 | ✅ 三项全 OK：`运行态 revision 与 HEAD 一致 → 714529d67bce`、`证据图片目录可写`、`5 个定时器均已启用` |
| 6 | 幂等：连跑两次全部 `[跳过]` | ✅ 见 T1/T2 |
| 7 | `--dry-run` 不改任何东西 | ✅ 卷列表与边缘配置的 md5 前后一致 |

### 6.2 最有价值的一条：属主修复用**真实容器 uid** 验证

不是看属主数字，而是真的以容器内的 uid 去写：

```text
chown -R root:root data/uploads
→ docker exec -u 1001 … touch → 写入失败 ✅（复现 EACCES，即缺口 5）
→ prepare-host.sh --fix-uploads → UPLOADS_OWNERSHIP=PASS
→ docker exec -u 1001 … touch → 成功 ✅
```

### 6.3 一个过程中的自我纠正

第一次测"建卷"分支时，我的测试脚本把 `docker volume rm` 的 stderr 丢进了 `/dev/null`，
**卷其实没删掉，于是"测试通过"是假的** —— 断言 `[跳过] 卷已存在` 我一度读成了 `[ OK ] 已创建`。

**又是同一个形状**：隐藏失败信号。修法是去掉 `2>/dev/null`，先断言"破坏成功"再断言"修复成功"。

## 7. 追加修正：`jq` / `flock` 被误列为「可选命令」

**触发**：用户问「脚本是否参考过 `docs/KnowTrace-VPS-部署学习-2026-09-06`」。
**答案是我此前没有系统读过那份从零部署教程** —— 只零散引用过它的 Caddyfile 快照与
`配置样例/`。补读之后，教程 §5 的安装清单里明确有 `jq`，而我的 `preflight.sh` 把
`jq` 归在「可选命令」，缺了只 `b_warn`「相关能力会跳过」。**这个提示语对 jq 是错的。**

### 7.1 实测依据

| 命令 | 仓库里的实际调用处 | 归在「可选」的后果 |
| --- | --- | --- |
| `jq` | **25 处**（`weekly-check.sh` / `monthly-ops.sh` 解析 JSON 报告） | 缺了不是"跳过"，是巡检**静默产出不完整报告** —— 调用点普遍带 `2>/dev/null`，失败被吞 |
| `flock` | **5 处**（并发锁） | 同上 |
| `bc` / `make` | **0 处** | 确实可选（`make` 只在 PowerShell 的 Makefile 里用） |

**并且 `jq` 在这台新机器上的存在是巧合**：`apt-mark showauto` 里有它、`showmanual` 里没有
—— 它是 **`fwupd` 的依赖顺带装上的**，换一个更精简的 Ubuntu 镜像就可能没有。

### 7.2 改动与验证

`lib/preflight.sh`：`jq`、`flock` 从「可选」移入「必需」；安装提示改为
`apt-get install -y git curl openssl python3 jq util-linux ca-certificates`。

**隔离验证**（造一个不含 jq / flock 的 PATH 农场）：

```text
新分类：[FAIL] 缺少必需命令：jq flock  → 预检拒绝运行  ✅
旧分类：[WARN] 缺少可选命令：make flock jq → 继续跑，巡检静默降级  ❌
```
