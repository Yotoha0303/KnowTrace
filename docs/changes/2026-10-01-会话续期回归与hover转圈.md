## 0. 先说最严重的：④ 是**我引入的回归**

`2026-10-01-体验三项修复.md` 那次我加了「Access Token 失效时自动续期」。
**它的守卫写错了，导致真实场景下续期从不触发。**

### 决定性证据【实测，线上 `254a2eb`】

```text
A 只有 refresh cookie（15 分钟后浏览器的真实状态）  → 307    ← 被踢到登录页
B access 失效 + refresh 有效                        → 200
C 两者都有效                                        → 200
```

### 根因

```ts
if (!user?.ok || !authorization?.ok) {
  if (accessToken) {                    // ← 错的守卫
    const renewed = await renewSession(request);
```

而 **access cookie 的 `maxAge` = `access_token_expires_in` = 900 秒**。
**15 分钟一到，浏览器直接删掉它** —— 于是真实场景是「**只有 refresh cookie，没有 access cookie**」，
`if (accessToken)` 不成立，**续期从不执行**。

**而 `renewSession` 根本不用 access token**（它只读 refresh cookie）——
**守卫写错了对象**。

### 我上次的"验证"验错了状态

`2026-10-01-体验三项修复.md` 的 4.5.1 写着「不必等 15 分钟：这个状态就足以决定分支」，
并用状态 **B** 验证通过。

**那个推理是错的**：15 分钟时 access cookie 是**不存在**，不是「存在但值无效」——
proxy 看到的是两种不同的输入。

### 佐证：日志里续期确实没在需要时发生

```text
13:15:12  GET /captures/...?_rsc=...  → 307   ← 预取被踢
13:15:13  GET /login?...              → 200
13:15:14  /api/v1/auth/refresh        → 200   ← **登录页**的自动恢复才刷新
```

认证服务里 `refresh` 只被调用 **4 次**，而登录 **26 次**——
**续期没在真正需要时触发，是登录页兜住了。**

（同时排除了另一个怀疑：`replay` 命中 **0 次**，**不是**并发刷新被判重放。）

## 1. ④ 的修法

**把守卫从「有没有 access token」改成「有没有 refresh token」** —— 因为
「access 过期」的**两种表现**（cookie 消失 / cookie 存在但无效）都该触发续期：

```ts
const hasRefreshToken = Boolean(request.cookies.get(REFRESH_TOKEN_COOKIE)?.value);
if (hasRefreshToken) {
  const renewed = await renewSession(request);
  if (renewed) return renewed;
}
```

`renewSession` 内部已经自己读 refresh cookie 并在拿不到时返回 `null`，
所以这个守卫只负责**决定要不要尝试**。

### 验收（三条都要过）

| 状态 | 期望 |
| --- | --- |
| A 只有 refresh cookie | **200**（原先 307）—— 这是本次要修的 |
| B access 失效 + refresh 有效 | 200（不能回退） |
| C 两者都有效 | 200（不能回退） |

**并补一条自动化测试**覆盖状态 A —— 现有测试只覆盖了 B，
而**恰恰是 B 掩盖了这个 bug**。

## 2. ① 与 ②：「悬浮时的循环加载动画」——真凶是 `cursor: wait`

**不是我上次说的 `isPending` 拖长**（那是我在 `reliability-panel` 修的另一件事）。

真凶是 CSS 里这一行：

```css
.button:disabled { opacity: .5; cursor: wait; }
```

**`cursor: wait` 就是操作系统级的旋转等待光标**——悬浮在 disabled 按钮上时，
**光标自己就在转**。而「开始调查」是 `disabled={isPending}` 且**没有 spinner**，
所以刷新期间悬浮它 → 看到转圈的等待光标。

【实测】`cursor: wait` 共 **4 处**（`globals.css:87,104,170,563`），
每一处都是「悬浮即转」。

### 修法

把 `cursor: wait` 改为 `cursor: not-allowed`：
后者表达「现在不能点」，**不自带动画**，语义也更准确——
按钮在等的是**数据回填**，不是「请稍候」。

**②（上传模块）是两件事叠加**：`cursor: wait` **加上** `isPending` 驱动的 spinner。
`cursor: wait` 随 ① 一并修；spinner 按 `reliability-panel` 的范式脱钩。

## 3. ③「上传图片后可以删除」——**这是一个缺失的功能，不是 bug**

【实测】全仓库**没有任何删除图片的入口**：

```
grep -E "deleteEvidenceImage|删除图片|removeImage" src/components src/features/claims
→ 空
```

要做得完整，至少需要：

| # | 部分 |
| --- | --- |
| a | 服务层：删除单张附件的函数（含**鉴权与归属校验**） |
| b | API 或 Server Action |
| c | 界面：每张图片旁的删除按钮 + 二次确认 |

**并且它牵涉一条产品规则**（`README.md`）：
「人工核验会冻结附件快照和组合哈希，**后续新增图片会使旧核验失效**」。
**删除图片同样会改变组合哈希** —— 所以删除也必须**使旧核验失效**，
否则会出现「核验通过但图片已变」的漏洞。

**这条不是一行能改完的**，本次**先做 ④①②**（都是明确缺陷），
③ 单独排期——**避免把功能开发混进缺陷修复**。
