## 1. 失败现象

演练跑到 `monitoring` 的 `[6/6]` 验收时失败，`install.sh` 退出码 1：

```text
[1/6] 拉取固定版本的核心监控镜像           ✅
[2/6] 让主应用加载私有 metrics token       ✅
[3/6] 安装 Nginx metrics 公网阻断          ✅
[4/6] 启动 Alertmanager/Exporter/Prom/Grafana ✅
[5/6] 断言运行态 revision  [ OK ] 与部署目录一致：c326e4ff47cb
[6/6] 端点/target/PromQL/Alertmanager/Grafana 验收
FAIL <urlopen error [Errno 111] Connection refused>
PASS KnowTrace liveness / readiness / Auth / Prometheus / Alertmanager / Grafana / 受保护指标
```

公网 HTTPS **000**（连不上）。

## 2. 根因链（三方证据）

| 证据 | 内容 |
| --- | --- |
| `prepare-host.sh` 第 96 行原注释 | 「这里只"放一份"，**不做 reload**」—— 全脚本无任何 `systemctl` 调用 |
| `install.sh` | **完全没有** systemctl 调用（nginx/caddy 只靠 apt 的 postinst 自启） |
| 机器实测 | `default` 站点**文件已删**，但 **nginx 仍占着 `0.0.0.0:80`**（运行中进程还持有旧配置） |

完整链条：

```text
apt install nginx caddy
  ↓ 两者都自启
nginx 带 default 站点抢到 0.0.0.0:80
  ↓
caddy 启动失败：Error: loading initial config: ...
                listening on :80: bind: address already in use
  ↓ caddy.service 进入 failed
prepare-host.sh 删掉 default 的【文件】——但运行中的 nginx 仍持有 :80
（配置改了不 reload，监听不会变）
  ↓ 此后再没人拉起 caddy
证书签不了 → 443 不监听 → 公网 000 → [6/6] Connection refused
```

## 3. 为什么之前"看起来能成"

2026-10-02 上午那次手工部署**是成功的** —— 因为我**手工敲过** `systemctl restart caddy`，
却**没有把它写进脚本**。

> **这正是"手工做过 ≠ 脚本会做"的典型**，也是本仓库一贯要防的那类问题：
> 人做对了，脚本没做，于是换台机器就失败。

## 4. 修复

`prepare-host.sh` 新增第 4 节（原第 4 节顺延为第 5 节）：

```text
--- 4/5 释放 :80 并启动 Caddy ---
  systemctl reload nginx          # 关键：让 nginx 按新配置重建 worker，交出 :80
  systemctl reset-failed caddy    # caddy 若处于 failed，必须先 reset 才能 restart
  systemctl enable caddy
  systemctl restart caddy
  → 校验 active，并打印 :80 当前持有者
```

**为什么 `reload` 而不是 `restart` nginx**：只要它按新配置重建 worker，:80 就释放了；
`reload` 不断连接、影响更小。

**为什么必须 `reset-failed`**：systemd 对 `failed` 状态的单元会拒绝 `restart`。

## 5. 验收（在**真实故障机**上验证，不是重建场景）

修复前该机正处于失败状态，直接跑修复后的脚本：

```text
修复前: caddy=failed   nginx=active   :80 持有者=nginx
修复后: caddy=active   nginx=active   :80 持有者=caddy(pid 23808)
        443 已监听
        证书已签发：/var/lib/caddy/.../certificates/acme-v02…/knowtrace.duckdns.org
        公网 HTTPS → 200
```

## 6. 边界与遗留

- 本次只修「:80 争抢导致 Caddy 起不来」这一条；**未改** monitoring 阶段本身。
- `install.sh` 仍然不代管 UFW / sshd（自锁风险，见各自记录）。
- 修复后需**重跑演练**以确认整条链（含 `monitoring` 的 [6/6]、`ops`、`verify`）走通。
