### 3.2 阶段 1：Ansible Day 0

按文档 §一 的四层分工，Ansible 只负责**操作系统本身**，且**不碰容器内配置**。

```
deploy/ansible/
├── ansible.cfg          # inventory 路径、remote_user=root、port=22345、host_key_checking
├── inventory.ini        # 45.64.74.99 ansible_port=22345
├── site.yml             # 只 import_role
├── group_vars/all.yml   # ssh 端口 / ufw 端口 / apt 包清单
└── roles/
    ├── baseline/        # apt 装包（与 install.sh 的 DEPS 对齐）+ unattended-upgrades
    ├── hardening/       # sshd drop-in + sysctl
    ├── firewall/        # ufw 默认策略 + 放行
    └── fail2ban/        # 确认 jail 指向实际 SSH 端口
```

**三条硬约束**（都是实测踩出来的）：

1. **`drop_in` 必须叫 `00-knowtrace-hardening.conf`**。
   实测主配置第 12 行是 `Include /etc/ssh/sshd_config.d/*.conf`，
   而 `50-cloud-init.conf` 里写着 `PasswordAuthentication yes` ——
   sshd 同参数**首个值生效**，排它后面（`99-*.conf`）会被盖掉，改了等于没改。
2. **`authorized_keys` 现在是空的**，所以「装公钥」是 Ansible 的第一件事，
   也是后面敢关密码登录的唯一前提。公钥沿用
   `C:\Users\Yotoha\.ssh\knowtrace_vps_ed25519.pub`（不新生成密钥）。
3. **`passwordauthentication no` 前必须有一道人工闸**：先跑只读断言确认密钥登录成功，
   由用户确认后才继续。且 Ansible 跑之前**必须先加载上一版 ufw 规则快照**
   （本机 `_ops-backups/` 有 2026-09-28 的副本），因为一旦规则加载把 22345 打掉、
   同时密码登录又关了，就会**结构性失联**（只能走厂商控制台）。

**幂等**：`sshd_config` 的 `lineinfile` 带 `validate: 'sshd -t -f %s'`；
`ufw` 用 `rule` 而非 `reset`；sysctl 用 `sysctl_set`。

## 5. 回滚

- **sshd**：drop-in 写入前备份到 `/root/knowtrace-ops/backups/<时间戳>/`；`sshd -t` 通过才 reload；
  **密码登录在人工闸通过前一直可用**，失联风险被结构性排除；兜底=厂商控制台。
- **UFW**：只增不减；先加载上一版规则快照；兜底 `ufw --force disable`。
- **git**：每阶段一个提交，`git revert` 可退；`deploy/ansible/` 是新增目录，删除即完全撤销。

### 7.2 执行中真实修掉的四个问题（每一个都值得单独记）

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `--check` 第一轮炸在断言 | `'port ' + ssh_port` —— `ssh_port` 是 **int**，不能与 str 拼接 | `(ssh_port \| string)` |
| 2 | 首次全量在 `hardening` 停下 | 配置写 `prohibit-password`，但 **`sshd -T` 归一化成 `without-password` 输出**。**配置完全正确，是断言写错** | 断言接受两种拼写 |
| 3 | `firewall` 断言恒假 | ufw 把端口打印在**行首**，而我查的是带前导空格的 `' 22345/tcp'`。纯子串 `'80/tcp'` 还会误命中 `8080/tcp` | `stdout_lines \| match`（锚定行首） |
| 4 | 幂等永远 `changed=1` | 「备份 sshd_config.d」dest 带时间戳，**每次跑都新建压缩包**；且写了 `changed_when: true` 硬编码 changed | 用「drop-in 不存在」判断仅首次备份，删掉硬编码 |

**问题 2 和 3 值得特别注意：方向与「部署看着成功」相反 —— 是绿灯被当成红灯。**
配置全部正确落地，失败纯粹来自我照着**配置文件的写法**写断言，
而没有先取样看命令**实际输出**什么。教训已写进 `deploy/ansible/README.md`。

**问题 4 是个反面教材**：为了"确保备份一定被执行"而写 `changed_when: true`，
恰好把要验的东西（幂等）弄坏了 —— 硬编码 changed 等于主动放弃幂等信号。

### 7.3 我自己的一个观测错误（记录在案）

诊断时我写了 `cmd | tail -45; echo "退出码=$?"`，而 `$?` 取的是 **tail** 的退出码 ——
playbook 明明 `failed=1` 却显示「退出码=0」。正确写法是 `${PIPESTATUS[0]}`。
**这与 2026-09-30 事故同属一类：「命令返回 0 不等于成功」。**
本记录 §2.1 已更正过两处类似误判，这是第三处 —— 都出在"我怎么读结果"上，
不在"东西本身对不对"上。

### 7.4 实际采用的路线（与原方案的一处偏离）

**Ansible 改为「在目标机上就地跑」**（`hosts: localhost` + `connection: local`），
不是原方案的「从 Windows 控制端推」。

原因：ansible-core 的 Windows 控制端支持是**坏的**，实测两版都跑不起来：

- `2.21.4` → `OSError: [WinError 87]`（`check_blocking_io()` 对控制台句柄失败）
- `2.17.14`（补掉上述后）→ `ERROR: No module named 'fcntl'`（POSIX 专有，无解）

两条替代路线（WSL 控制端 / dediko 容器）的否决理由见 `deploy/ansible/README.md`。
就地跑的附带好处：不需要第二个账号、不需要二次 SSH 认证。
本地那次 `uv tool install ansible-core` 已 `uninstall` 干净，未在用户环境留残留。
