# 变更记录

产品侧的**变动前记录**。每次修改代码或配置之前，先在这里写清楚：
要改什么、为什么、怎么验收、怎么回滚。

## 为什么要这个目录

在此之前，`KnowTrace-ops/docs/` 有日期化的执行记录，但**产品侧没有**。
后果在缺陷 D-03 上已经显现：

> 一个完整的事故根因报告躺在 `docs/KnowTrace-VPS-部署学习-2026-09-06/阶段一/问题记录/`
> 这个**运维学习目录**里，而产品侧的 `docs/17` 还在写「初步推断」。
> **信息传导断裂，导致 8 项修复一项没做。**

本目录补的就是这个位置：**产品侧的改动，在这里留痕。**

## 与其他文档的分工

| 目录 | 记什么 | 什么时候写 |
| --- | --- | --- |
| `docs/changes/`（本目录） | **产品侧的每一次变动**：改什么、为什么、验收、回滚 | **变动前** |
| `../KnowTrace-ops/docs/` | 运维侧的执行记录与事故复盘 | 操作后 |
| `docs/13`~`docs/21` | 产品状态、缺陷清单、计划 | 状态变化时 |
| `docs/adr/` | 架构决策 | 决策时 |

## 命名与结构

```
docs/changes/YYYY-MM-DD-<简短主题>.md
```

每份记录至少包含：

1. **变动范围** —— 涉及哪些文件
2. **依据** —— 由哪个缺陷/需求驱动，有什么证据
3. **改动方案** —— 具体改什么
4. **验收（可判定）** —— 怎么证明它被修好了，**必须可执行**
5. **回滚** —— 出问题怎么退回去
6. **边界** —— 本次明确做什么

第 4 条是硬要求：沿用本项目的纪律——
**「命令返回 0」不算验收，「状态改变」才算**。
参见 `../KnowTrace-career-assets/10-工程积累/E-01-部署成功的判据不能是命令返回0.md`。

## 先记录，再动手

顺序不能反：

```
1. 写记录（含验收标准）  ← 此时代码还没改
2. 提交记录
3. 改代码
4. 跑验收，把结果填回记录的「执行结果」一节
5. 提交代码
```

**为什么记录要先进 git**：这样「当时的意图」和「实际的结果」是两次提交，
事后能看出**计划与实现的差异**——而差异往往比结果本身更有信息量。
