## 1. 现象

2026-10-01 部署 `66c1a36` 时，验收脚本以 **401** 失败：

```
$ python3 scripts/linux/verify-observability.py --core
FAIL HTTP Error 401: Unauthorized        ← stderr（无缓冲，所以先于 stdout 出现）
PASS KnowTrace liveness: HTTP 200
PASS KnowTrace readiness: HTTP 200
...
PASS Prometheus to Alertmanager discovery: active=1
退出码=1
```

**所有 PASS 都通过了**，401 发生在它们**之后**——对应脚本里紧跟
`Prometheus to Alertmanager discovery` 之后的 **Grafana API 查询**。

---

## 2. 根因：Grafana 的管理密码**只在首次启动时**从环境变量读入

**【实测】证据链**：

| 事实 | 值 |
| --- | --- |
| Grafana 数据卷创建 | **2026-09-08 03:04:51** |
| Grafana 容器首次启动 | 2026-09-08 03:04:52 |
| **`.env.observability` 生成** | **2026-09-28 16:07:15**（20 天后） |
| Grafana 容器自那以后是否重启过 | **否** |
| 容器 env 里的 `GF_SECURITY_ADMIN_PASSWORD` 与 `.env.observability` | **一致** |
| 用该密码查 `http://127.0.0.1:3001/api/search` | **401** |

**Grafana 的行为**：`GF_SECURITY_ADMIN_PASSWORD` 只在 `grafana.db` **不存在**时用于创建管理员；
一旦数据卷里有了库，该环境变量**不再生效**，密码以库中的值为准。

所以：**`.env.observability` 里的那个密码从来没匹配过**——
它是 09-28 由 `init-observability-env.sh` 重新生成的，
而 Grafana 的密码是 09-08 就固化在卷里的。

### 一个连带影响（我自己造成的）

验收失败导致 `set -Eeuo pipefail` 让脚本**提前退出**，
使我的 `[6/6] 断言运行态 revision` **从未执行**——
`knowtrace_app_revision_match` 因此停在**过期值**。

**这是那个修复的顺序缺陷**：断言排在验收之后，就会被验收的失败挡住。
已单独修（见 `2026-10-01-体验三项修复.md` 的后续，以及本次的脚本重排）。

## 4.1 连带修复：把 `[6/6]` 断言移到验收之前

**⚠️ 顺序偏差声明**：这一项我在写本记录**之前**就改了（已改、未提交）。
按本目录的约定应该先记录——**这里如实标注**，而不是假装顺序是对的。

**改动**：`scripts/linux/deploy-observability.sh` 的两段调换顺序

```
改前：[1/5] 拉镜像 → [2/5] 重建应用 → [3/5] Nginx → [4/5] 起监控
      → [5/5] 验收  → [6/6] 断言运行态 revision      ← 被验收的失败挡住

改后：[1/6] … [4/6]（不变）
      → [5/6] 断言运行态 revision                     ← 先断言
      → [6/6] 验收                                    ← 再全面验收
```

**理由**：断言是**部署是否生效**的判据；验收是**外围设施是否健康**的体检。
判据必须**先**执行——否则外围的一个小毛病就能让「部署有没有生效」这个问题失去答案。
本次就是这样：Grafana 401 → 脚本退出 → 断言没跑 → `knowtrace_app_revision_match` 停在过期值。

**这也修正了我原设计的一个缺陷**：把断言放在最后，
等于让它依赖「验收全过」这个与它无关的前提。

## 5. 本次做什么 / 不做什么

### 做：把失败**讲清楚**，并提供**诊断路径**

| # | 改动 | 理由 |
| --- | --- | --- |
| a | Grafana 401 时给出**明确的失败原因**（凭据漂移 + 数据卷缓存），而不是一句 `HTTP Error 401` | 现在的报错需要读完整个脚本才知道是 Grafana；下次遇到的人不该再走一遍这条弯路 |
| b | 新增 `--check-grafana-auth` 诊断模式：**只**检查凭据能否登录，输出可执行的修复指引 | 从「验收失败」到「知道怎么办」之间不该靠猜 |

### ~~不做：不重置 Grafana 密码~~ → ⚠️ **本条已被修正（2026-10-01）**

> **原判断**：修它只能**重置 Grafana 密码**，而那要销毁 `grafana.db`，
> 为修一个验收脚本的可用性去动生产数据卷，代价与收益不成比例。
>
> **这个判断建立在错误的二选一上。** 拿到 Grafana 的实际密码后（`admin` / 用户提供），
> 发现正确方向是**反过来**：

| 方向 | 做法 | 代价 |
| --- | --- | --- |
| ❌ 我原先以为的 | 重置 Grafana → 销毁 `grafana.db` | 丢卷里所有内容 |
| ✅ **实际可行** | **把 `.env.observability` 里的 `GRAFANA_ADMIN_PASSWORD` 改成 Grafana 实际持有的值** | **零** |

**为什么改 .env 侧是对的**：
- 该变量**只在数据卷为空时生效**，所以改它**不会**去改 Grafana 里的密码——
  它只是让**验收脚本**与 Grafana 的现状对齐。
- 不重启、不销毁任何东西，**`grafana.db` 一字不动**。
- 验收脚本读的就是这个文件（`verify-observability.py` 的 `read_env(.env.observability)`）。

**代价的诚实说明**：`.env.observability` 的权限是 `600`，明文存密码——
但这**本来就是它的设计**（Grafana 密码、metrics token 都在里面）。
本次只是把其中一个值改成**实际生效的那个**，没有新增暴露面。

**新增的运维含义（必须写明）**：
> 从此以后，**Grafana 的管理密码由 `grafana.db` 决定，不由 `.env.observability` 决定**。
> 改 `.env.observability` 里的那个值**不会**改变 Grafana 的登录密码；
> 若哪天真要换，必须走重置流程（删卷或 `grafana-cli admin reset-admin-password`），
> 并**同时**更新 `.env.observability` 让两者重新一致。

### 怎么改（已执行，见第 7 节）

```bash
# 只改这一个键，不动其它行
sed -i 's|^GRAFANA_ADMIN_PASSWORD=.*|GRAFANA_ADMIN_PASSWORD=<Grafana 实际持有的值>|'   /opt/knowtrace/.env.observability
chmod 600 /opt/knowtrace/.env.observability
# 不重启任何容器 —— 该变量对运行中的 Grafana 本来就无效
```
