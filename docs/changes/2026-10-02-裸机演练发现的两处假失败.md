# 2026-10-02 裸机演练发现的两处假失败（首次部署被误判为故障）

| 项 | 值 |
| --- | --- |
| 记录时间 | 2026-10-02（变动后补记） |
| 发现方式 | 裸机演练：`install.sh --all` 在重装后的 Ubuntu 24.04 上跑到 monitoring/verify |
| 变动范围 | `scripts/linux/verify-observability.py`、`scripts/bootstrap/bootstrap.sh` |
| 性质 | **都是"把首次部署的正常状态误判为失败"** —— 会中断整条一键链 |

---

## 1. 缺陷 A：备份指标在首次部署时被当成硬要求

`verify-observability.py` 的 `[6/6]` 验收里：

```text
FAIL Prometheus 查询没有有效样本：knowtrace_backup_archive_count >= 1
```

**新装机器上这个指标必然为 0** —— 备份由 `knowtrace-backup.timer` 当晚才触发。
于是 `monitoring` 阶段退出码 1，整条链断在这里。

### 修法：区分「首次部署」与「指标坏了」

| 情形 | 判定 |
| --- | --- |
| 备份目录**没有**归档、指标为 0 | **PASS** —— 首次部署的正常状态（并说明 timer 触发后会转为 >= 1） |
| 备份目录**有**归档、指标为 0 | **FAIL** —— 指标写入链路坏了（这才是真故障） |

判据用的是「本地归档数」与「指标值」的**一致性**，而不是"指标必须 >= 1"这个形式。

## 2. 缺陷 B：我把可选的 offsite 定时器写成了必需

`verify` 阶段的定时器断言（**我自己在本次演练前新加的**）把 5 个 timer 一并要求：

```text
[FAIL] 未启用的定时器：offsite-backup
```

但 `offsite-backup` 需要 **age 公钥 + rclone 远端**，属"刻意不自动化"那一类
（外部凭据与后端选择）。新机器上它必然未启用 —— **这是设计如此，不是故障**。

### 修法：必需 4 个，可选 1 个

```text
必需：backup / daily-ops / weekly-check / monthly-ops
可选：offsite-backup —— 未启用时打印说明而非 FAIL
```

## 3. 为什么这两处值得单独记

两处的**形状相同**：**把"尚未发生"当成"已经出错"**。
在已部署的机器上永远测不出来 —— 那里备份早就有、offsite 早就配好了。
**只有真正从零跑一遍才会暴露。**

这与本仓库最贵的教训是同一族：
2026-09-30 是"**看起来成功了**"（假成功），这两处是"**看起来失败了**"（假失败）。
**两者都源于判据没有区分"状态未达到"与"状态错误"。**

## 4. 验收（实测）

```text
修复后重跑 monitoring:
  PASS PromQL: 尚无备份归档（首次部署的正常状态；timer 触发后本项会转为 >= 1）
  RESULT all requested observability checks passed        → 退出码 0

修复后重跑 verify:
  [ OK ] 4 个必需定时器均已启用
  [ OK ] 验收通过                                          → 退出码 0
  [WARN] 异地备份未配置（可选，说明而非失败）
```

## 5. 边界

- 未改 `deploy-observability.sh` 装备份 timer 的顺序（它本来就正确）。
- 未给 `verify-observability.py` 引入通用 WARN 机制 —— 只对这一项做了分类判别，
  避免为改一处而动整个失败收集结构。
