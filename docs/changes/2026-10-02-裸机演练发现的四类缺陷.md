## 0. 主结论：这四类之前为什么都没被发现

**四类的形状完全相同：只在真正"从零"跑一遍时才会出现。**

| 缺陷 | 在**已部署**的机器上为什么遇不到 |
| --- | --- |
| nginx default 站点抢 `:80` → Caddy 起不来 | default 早删了 |
| 备份指标 `>= 1` 在首次部署时为 0 | 备份早有了 |
| `offsite-backup` 定时器未启用 | 早配好了（属可选） |
| apt 撞 dpkg 锁（开机时 329 个包在下载） | 早过了开机窗口 |

> **所以 `--all` 在已部署机器上重跑，不能替代裸机演练。**
> 2026-10-02 之前所有"手工验证成功"都不算数 —— 那些操作恰好绕开了全部四类。
> 这与本仓库最贵的教训同族：2026-09-30 是「**看起来成功了**」（假成功），
> 其中三是「**看起来失败了**」（假失败）。**两者都源于判据没区分"状态未达到"与"状态错误"。**

## 1. Caddy 与 nginx 争 `:80` —— 阻塞（HTTPS 全挂）

### 现象

`monitoring` 的 `[6/6]` 验收失败，`install.sh` 退出码 1，公网 HTTPS **000**：

```text
[5/6] 断言运行态 revision  [ OK ] 与部署目录一致
[6/6] 端点和 PromQL 验收
FAIL <urlopen error [Errno 111] Connection refused>
PASS liveness / readiness / Auth / Prometheus / Alertmanager / Grafana / 受保护指标
```

### 根因链（三方证据）

| 证据 | 内容 |
| --- | --- |
| `prepare-host.sh` 原注释 | 「这里只"放一份"，**不做 reload**」—— 全脚本无任何 `systemctl` 调用 |
| `install.sh` | **完全没有** systemctl 调用（nginx/caddy 只靠 apt 的 postinst 自启） |
| 机器实测 | `default` 站点**文件已删**，但 **nginx 仍占着 `0.0.0.0:80`**（运行中进程还持有旧配置） |

```text
apt install nginx caddy → 两者都自启
  → nginx 带 default 站点抢到 0.0.0.0:80
  → caddy 启动失败：listening on :80: bind: address already in use
  → caddy.service 进入 failed
  → prepare-host.sh 删掉 default 的【文件】，但运行中的 nginx 仍持有 :80
     （配置改了不 reload，监听不会变）
  → 此后再没人拉起 caddy
  → 证书签不了 → 443 不监听 → 公网 000 → [6/6] Connection refused
```

**为什么之前"看起来能成"**：上午那次手工部署是成功的 —— 因为我**手工敲过**
`systemctl restart caddy`，却**没有把它写进脚本**。**手工做过 ≠ 脚本会做。**

### 修法

`prepare-host.sh` 新增一节（原第 4 节顺延为第 5 节）：

```text
--- 4/5 释放 :80 并启动 Caddy ---
  systemctl reload nginx          # 让 nginx 按新配置重建 worker，交出 :80
  systemctl reset-failed caddy    # systemd 对 failed 的单元会拒绝 restart
  systemctl enable caddy
  systemctl restart caddy
  → 校验 active，并打印 :80 当前持有者
```

`reload` 而非 `restart` nginx：只要它按新配置重建 worker，`:80` 就释放了；`reload` 不断连接。

### 验收（在**真实故障机**上，不是重建场景）

```text
修复前: caddy=failed   nginx=active   :80 持有者=nginx
修复后: caddy=active   nginx=active   :80 持有者=caddy(pid 23808)
        443 已监听；证书已签发；公网 HTTPS → 200
```

## 2. 备份指标在首次部署被判 FAIL —— 假失败

`verify-observability.py` 的 `[6/6]` 里把 `knowtrace_backup_archive_count >= 1` 当硬要求：

```text
FAIL Prometheus 查询没有有效样本：knowtrace_backup_archive_count >= 1
```

**新装机器上该指标必然为 0** —— 备份由 `knowtrace-backup.timer` 当晚才触发。

### 修法：判别「首次部署」与「指标坏了」

| 情形 | 判定 |
| --- | --- |
| 备份目录**没有**归档、指标为 0 | **PASS** —— 首次部署的正常状态（并说明 timer 触发后会转为 >= 1） |
| 备份目录**有**归档、指标为 0 | **FAIL** —— 指标写入链路坏了（这才是真故障） |

判据用「本地归档数」与「指标值」的**一致性**，而不是"指标必须 >= 1"这个形式。

## 3. 可选的 `offsite-backup` 被当成必需定时器 —— 假失败

`verify` 阶段的定时器断言（本次演练前我自己新加的）把 5 个 timer 一并要求：

```text
[FAIL] 未启用的定时器：offsite-backup
```

但 `offsite-backup` 需要 **age 公钥 + rclone 远端**，属"刻意不自动化"那一类
（外部凭据与后端选择）。新机器上它必然未启用 —— **设计如此，不是故障**。

### 修法

```text
必需：backup / daily-ops / weekly-check / monthly-ops
可选：offsite-backup —— 未启用时打印说明而非 FAIL
```

## 4. apt 撞上 dpkg 锁 —— 阻塞（第一步就断）

### 现象

一行命令在**装依赖**这一步失败，退出码 100：

```text
E: Could not get lock /var/lib/dpkg/lock-frontend.
   It is held by process 37892 (unattended-upgr)
```

### 为什么会这样（实测数据）

新装 Ubuntu **开机后会触发 `unattended-upgrades`**：

```text
$ ps -o pid,etime,cmd -p 37892
  37892  01:14  /usr/bin/python3 /usr/bin/unattended-upgrade --download-only

$ apt-get -s upgrade | grep -c '^Inst'
  329                      ← 329 个包待升级
```

**329 个包**的 `--download-only` 阶段占锁**数分钟**，不是瞬时冲突。

### 修法

```text
1) 先用 fuser 检测锁并说明是谁在占、为什么 —— 免得用户以为脚本卡死
2) 用 apt 自带的 -o DPkg::Lock::Timeout=900 等锁（15 分钟），而不是立刻失败
```

超时取 15 分钟的依据：2 vCPU 上下载 329 个包通常几分钟，**留足余量胜过中途失败**
（最初想用 300 秒，实测看到 329 个包后改成 900）。

### 验收

人为占住锁 90 秒后跑一行命令：

```text
[WARN] dpkg 锁被占用：root (pid 39890)
       本步骤会等待，最多 15 分钟；不需要你干预。
[ OK ] 已安装：docker.io … jq util-linux openssl python3      ← 等住并装完
```

## 6. 附：我在修这些缺陷时**自己引入又当场修掉**的三个 bug

| bug | 现象 | 根因 |
| --- | --- | --- |
| `prepare-host.sh` 缺 `info()` 定义 | 在 `set -e` 下直接中止 | 新写的代码调了 `info "..."`，但该脚本只定义了 `ok/skip/warn/fail` |
| `install.sh` 的 `usage()` 用 `sed` 读 `$0` | `curl … \| bash -s -- --help` 报 `sed: can't read …` | 管道调用下没有脚本文件可读 —— **而管道正是文档主推的用法** |
| 测试脚本删掉自己的工作目录 | `fatal: Unable to read current working directory` | 清理脚本先 `cd /opt/knowtrace` 又 `rm -rf` 它。已在 `install.sh` 开头加 `cd /` 加固 |

第 2 个值得记：**它坏的正是最推荐的用法**，而我用 `bash scripts/install.sh` 本地测时完全正常。
**验证要按文档的用法来，不是按自己方便的用法。**
