# 2026-10-02 裸机演练发现的阻塞：apt 撞上 dpkg 锁

| 项 | 值 |
| --- | --- |
| 记录时间 | 2026-10-02（变动后补记） |
| 发现方式 | 裸机演练：清空部署后用文档里那条 `curl … \| bash` 一行命令重跑 |
| 变动范围 | `scripts/install.sh` |
| 性质 | 裸机特有 —— **已部署的机器上永远遇不到** |

---

## 1. 现象

一行命令在**第一步（装依赖）**就失败，退出码 100：

```text
==> 系统依赖
E: Could not get lock /var/lib/dpkg/lock-frontend.
   It is held by process 37892 (unattended-upgr)
E: Unable to acquire the dpkg frontend lock …, is another process using it?
############ 一行命令退出码: 100 ############
```

## 2. 为什么会这样（实测数据）

新装 Ubuntu **开机后会触发 `unattended-upgrades`**。实测该机：

```text
$ ps -o pid,etime,cmd -p 37892
  37892  01:14  /usr/bin/python3 /usr/bin/unattended-upgrade --download-only

$ apt-get -s upgrade | grep -c '^Inst'
  329                      ← 329 个包待升级
```

**329 个包**的 `--download-only` 阶段会占锁**数分钟**，不是瞬时冲突。

**为什么之前没遇到**：所有先前的验证都在**已部署的机器**上做 ——
那些机器早过了开机窗口，`unattended-upgrades` 早已跑完。

## 3. 修法

```text
1) 先说明谁在占、为什么 —— 免得用户以为脚本卡死
2) 用 apt 自带的 -o DPkg::Lock::Timeout=900 等锁（15 分钟），而不是立刻失败
```

超时取 15 分钟的依据：2 vCPU 上下载 329 个包通常几分钟，**留足余量胜过中途失败**。
（最初想用 300 秒，实测看到 329 个包后改成 900。）

## 4. 为什么值得单记

与同日发现的另两处（Caddy :80 争抢、备份指标假失败）**形状相同**：
**都是"只在真正从零跑一遍时才会出现"的问题。**

| 失败 | 在已部署机器上 |
| --- | --- |
| dpkg 锁被 unattended-upgrades 占 | 遇不到（早跑完了） |
| nginx default 站点抢 :80 导致 Caddy 起不来 | 遇不到（default 早删了） |
| 备份指标 >= 1 在首次部署时为 0 | 遇不到（备份早有了） |

**这三条合起来是同一个结论**：`--all` 在**已部署机器**上重跑**不能替代**裸机演练。
本文件与另两份记录（`…Caddy与80端口冲突.md`、`…两处假失败.md`）都是这次裸机演练的产物。
