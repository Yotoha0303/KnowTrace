## 1. 之前为什么"不能一键"——只有一个缺口

`bootstrap.sh` 本身**已经能**一条命令跑完 `host → apps → monitoring → ops → verify`。
缺的是**鸡生蛋**：它在仓库里，要跑它得先有仓库，要拿仓库得先 `git clone`，
而"装系统依赖 + clone"本身也该由脚本做 —— **所以在仓库之外需要一个入口**。

【实测】改前 `ls scripts/install*.sh install.sh` 为空：**这个入口从来不存在**。

## 2. 改动

新增 `scripts/install.sh`（bash，无外部依赖）：

```bash
sudo bash scripts/install.sh --domain knowtrace.example.org
# 或不先 clone：
curl -fsSL <raw-url>/scripts/install.sh | sudo bash -s -- --domain knowtrace.example.org
```

| 步骤 | 做什么 | 依据 |
| --- | --- | --- |
| 环境识别 | **只支持 Ubuntu/Debian**，其它发行版明确拒绝 | 包名与 apt 按 Debian 系写；避免"装到一半失败留半成品" |
| 系统依赖 | `docker.io docker-compose-v2 nginx caddy rclone age fail2ban git curl ca-certificates jq util-linux` | `preflight.sh` 的必需命令 + 教程 §5；`jq`/`flock` 是必需（巡检 26 处 jq 调用） |
| 仓库 | clone 或快进更新；有未跟踪改动只提示不擅自删 | 2026-10-01 踩过"未跟踪文件挡 pull" |
| 数据卷 | 建两个 `external` 卷 | 与 `host` 阶段双保险 |
| Caddyfile | **按 `--domain` 生成** | 与域名强相关，**不该把具体域名硬编码进仓库** |
| 交给 bootstrap | `bootstrap.sh --all` | 复用既有编排，不重复实现 |

**内存预警**：可用内存 < 700 MiB 时告警并给三条出路（别处构建 / 加 swap / 换机器）。

## 3. 验收（可判定）

| # | 标准 |

## 4. 执行结果（2026-10-02 实测）

> 本脚本在真机演练中暴露的四类缺陷见
> [`2026-10-02-裸机演练发现的四类缺陷.md`](2026-10-02-裸机演练发现的四类缺陷.md)。

全部 6 项通过。过程中**修掉两个真 bug**：

| bug | 现象 | 根因 |
| --- | --- | --- |
| `usage()` 用 `sed` 读 `$0` | `curl … \| bash -s -- --help` 报 `sed: can't read …` —— **而管道正是本脚本的头号用法** | 管道调用下没有脚本文件可读。已改为**内嵌 usage 文本** |
| dry-run 的假故障 | 全新机器 dry-run 最后报 `缺少 …/bootstrap.sh` 并中止 | dry-run 下 clone 只被打印、没真执行，却仍去检查文件。已按 `DRY_RUN` 分支 |

第 1 个值得记：**它坏的正是最推荐的用法**，而我在本地用 `bash scripts/install.sh` 测时完全正常 ——
只有按文档里那条 `curl | sudo bash` 去测才会暴露。**验证要按文档的用法来，不是按自己方便的用法。**

## 5. 边界

| 不做 | 原因 |
| --- | --- |
| UFW / sshd 加固 | 自锁风险（`ufw enable` 前未放行 SSH 端口会失联且无法远程改回） |
| 异地备份 / 告警邮箱 / AI key | 需外部凭据与后端选择 |
| 改 `bootstrap.sh` 的阶段语义 | 本次只新增入口，不动既有编排 |
| 写死域名 | 由 `--domain` 生成，不硬编码进仓库 |

## 6. 回滚

回滚 = `git revert` 本次提交。`install.sh` 本身不在任何镜像里，
且它的系统改动都是幂等可列出的（apt 装包、一个 Caddyfile、两个卷）。

## 7. 追加修正：依赖清单漏了 `openssl` 与 `python3`（2026-10-02，实测发现）

**触发**：用户追问「目前能否从 0 到 1 一键部署」。逐项核对时发现，
我在 §2 写的依赖清单 **漏了两个硬要求**。

### 7.1 它们是硬要求，不是"有就用"

| 依据 | 内容 |
| --- | --- |
| `scripts/linux/init-env.sh:58-59` | `command -v python3 \|\| exit 3`（openssl 同理）—— **缺即脚本失败** |
| `scripts/linux/write-ops-metrics.sh:49` | 同样硬要求 `python3` |
| `scripts/bootstrap/lib/preflight.sh:20` | `openssl`、`python3` 都在必需命令列表里 |

**为什么当时没发现**：它们在 Ubuntu 上常因基础包或依赖**碰巧存在** ——
实测这台机器上 `openssl` 是 **fwupd 的 auto 依赖**（`apt-mark showauto` 有、`showmanual` 无），
`python3` 来自 `python3-minimal`。**"本机能跑"不等于"下一台也能"。**

### 7.2 用纯净容器实测（比云厂商镜像更严格）

在服务器上用 Docker 起**纯净 `ubuntu:24.04`**（官方最小镜像，是保守测试）：

```text
装依赖【之前】—— preflight 的 10 项必需命令满足情况：
  git **缺** · docker **缺** · openssl **缺** · curl **缺** · python3 **缺** · jq **缺**
  （有的：awk sed grep flock）

装 install.sh 的清单【之后】（已含补上的 openssl、python3）：
  ✅ 10 项必需命令全部满足
  ✅ docker compose 2.40.3+ds1-0ubuntu1~24.04.1 可用
```

**结论**：补之前，纯净镜像上 **6/10 缺失**，包括我刚漏的那两个 ——
**不补则必然失败，而且是在 `apps` 阶段之前就失败**。

### 7.3 命令清单是核对出来的，不是猜的

从全仓库提取**所有被显式检查的命令**（`command -v` / `require_command` /
`ops_require_cmds` / `ops_have_cmd`），共 **44 个**，再按"硬失败还是可选"分类：

| 类别 | 命令 |
| --- | --- |
| **硬要求**（`\|\| exit` 或 `ops_require_cmds`） | `git docker openssl awk sed grep curl python3 jq flock ps stat df find head tail sort date hostname` |
| 可选（`ops_have_cmd`，没有就少一项检查） | `sar ufw last unattended-upgrades systemctl ss free journalctl` |
| Ubuntu essential / coreutils，必然存在，不列 | `tar sha256sum tr wc cmp diff mktemp rm install readlink od` |

`install.sh` 的清单现已覆盖全部硬要求；可选的那几个（`sar`=sysstat、`ufw` 等）
**保持不装** —— 它们只影响巡检的报告丰富度，且 `ufw` 属"自锁风险、不代做"那一类。
