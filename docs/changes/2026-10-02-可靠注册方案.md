## 0. 先说清「可靠」在这套系统里指三件事

| # | 要求 | 为什么必须有 | 现状 |
| --- | --- | --- | --- |
| 1 | **证明身份可控** | 否则是匿名建号 | ❌ 只收用户名密码 |
| 2 | **防批量滥用** | 否则可脚本化刷号 | ❌ 注册无限流、无验证码 |
| 3 | **不暴露已有数据** | 见 `2026-10-01-注册防滥用与数据暴露.md` | ❌ **必然暴露**（三机制叠加） |

**第 3 条是 2026-10-01 实测发现的**，也是最容易被忽略的一条：
新用户自动进默认空间 + member 可读 shared + **管理员的 private 会被自动改回 shared**
⇒ **任何注册者必然能读到管理员的全部记录**。

**所以「可靠注册」不只是加一道验证，还要让第 3 条重新成立。**

## 2. 四个方案

### 方案 A —— 邮箱验证（= FEAT-006 的完整实现）

| | |
| --- | --- |
| 做什么 | `users` 加 `email` / `email_verified_at`；新增验证令牌表；接入 SMTP 发信；注册流程改为「提交 → 收信 → 点链接/填码 → 激活」 |
| 工程量 | **大**。含验证码签发、过期、重发限流、防枚举 |
| 依赖 | 163 SMTP 凭据（已有） |
| 风险 | 改 subtree 的账号模型；邮件送达率不受控；**自己发信的运维负担长期存在** |

### 方案 B —— 邀请制 ⭐ **推荐**

| | |
| --- | --- |
| 做什么 | 管理员生成一次性邀请码；注册时必须携带；码可设有效期与使用次数 |
| 工程量 | **小**。一张 `invitations` 表 + 注册时校验 |
| 依赖 | **无**——不发邮件、不依赖第三方 |
| 关键收益 | **不需要邮件设施**，绕开 FEAT-006 里最大的一块工程量 |

### 方案 C —— 第三方 OAuth（GitHub / Google）

| | |
| --- | --- |
| 做什么 | go-user-system 接入 OAuth 授权码流程 |
| 工程量 | 大 |
| 收益 | 不自己发信、不存密码、身份由第三方保证 |
| 代价 | 引入外部依赖与凭据管理；对「自托管/私有化」定位是**逆风** |

### 方案 D —— 维持关闭

零成本，但用户明确想要注册。

## 3. 为什么推荐 **B（邀请制）**，而不是 FEAT-006 的 A

**这是我与你自己写下的 FEAT-006 的不同意见，理由如下：**

### 理由 1：邀请制**让既有设计重新成立**，而 A 不会

那三条暴露机制里，「新用户自动进默认空间 + member 可读 shared」
**在「可信小群体」前提下是设计意图**（ADR-0015 明写：管理员内容默认共享）。

**暴露问题只在「注册对陌生人开放」时才成立。**
邀请制把注册门槛交回**可信的人**手里——**这不是打补丁，是把设计前提恢复回来**。

而 A（邮箱验证）**不解决这一点**：陌生人只要有邮箱仍可注册，
于是**仍然必然读到管理员内容**。

### 理由 2：产品定位就是「个人 / 小群体」

`README.md`：「面向个人或在同一可信环境中使用的小群体」。
`00-product-brief.md` 的适用场景是「几个人在同一可信局域网中共享一套记录」。

**邀请制与这个定位天然吻合**；自助注册（A）是为「面向公众」准备的，
而项目**明确把自己排除在那一类之外**。

### 理由 3：工程量差一个数量级

A 要建：邮箱字段 + 验证表 + SMTP 集成 + 令牌签发/过期/重发 + 防枚举 + 送达率处理。
B 要建：一张邀请表 + 注册时校验。

**在「还没有第二个真实用户」的现在**（认证库 2 个账号，都是我们自己建的），
把 A 的工程量投进去**是过早建设**——正是 `00-product-brief.md` 问题四警告的那类。

### 理由 4：不发信 = 少一类长期运维负担

邮件送达率、SMTP 限流、退信处理、被标记垃圾邮件——**这些是没有出口的长期工作**。
告警邮件已经引入了 SMTP（`ALERT_SMTP_*`），但那是**运维必需**；
注册验证邮件是**可选的产品功能**，用邀请制就绕开了。

## 4. 若选 B，还需要一并解决的

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 邀请表 + 签发/校验 | 核心 |
| 2 | **注册限流** | 邀请码也有被爆破的风险（码要足够长且一次性） |
| 3 | **新用户进哪个空间** | 邀请时**指定**加入哪个 workspace 与角色——比"自动进默认空间"更可控 |
| 4 | 管理员签发邀请的界面 | 或先用 CLI/SQL 签发，界面后补 |

**第 3 条是顺带把 2026-10-01 那个暴露问题一起修了**：
邀请制天然允许「邀请谁、进哪个空间、什么角色」——不必再自动塞进默认空间。

## 5. 建议的执行顺序

```text
① 先关注册（立刻消除暴露面）
② 邀请制：邀请表 + 校验 + 限流
③ 邀请时指定 workspace 与角色（顺带修暴露问题）
④ 界面（管理员签发邀请）
```

**①可以立刻做**，且不影响任何已完成的事（`KnowTraceReviewer` 已建好）。
