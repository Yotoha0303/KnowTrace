## 1. 实测：切换界面时现在是什么体验

**服务端本身不慢**【实测，登录后逐页测】：

| 页面 | 服务端耗时 |
| --- | --- |
| `/` | 0.331s |
| `/claims` | 0.131s |
| `/search` | 0.084s |
| `/categories` | 0.071s |
| `/subjects` | 0.061s |
| `/archived` | 0.068s |

**但用户感知由三件事决定，而它们全是缺的**【实测】：

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | **`loading.tsx` 数量 = 0** | 点击导航后**没有任何即时反馈**，界面要等新页面**完全渲染完**才切换 |
| 2 | **14 个页面里 10 个 `force-dynamic`** | 每次导航都必须回服务端完整渲染，拿不到缓存 |
| 3 | **导航无 pending 指示**（`useLinkStatus` / `isPending` / `Suspense` 全无） | 等待期间界面像"卡住"，诱导重复点击 |

**所以体感是**：点击 → 界面纹丝不动 → 等 0.06–0.33s → 整页换掉。**没有过渡、没有骨架、没有 loading。**

## 2. 与本次会话已做三项的关系（避免误解）

| 已做 | 对切换体验的作用 |
| --- | --- |
| 静态资源 `immutable` | **无** —— 只优化首次加载 |
| 会话续期 | **无直接作用** —— 是修 bug（避免切换时被踢到错误页），不是提速 |
| 保存快捷键 | **无** —— 与导航无关 |

**用户问的正是这块，而它此前没有被碰过。**

---

## 3. 根因

一个**结构性选择**：为"数据永远新鲜"，10 个页面选了 `force-dynamic`。
代价是每次切换都一次完整的服务端往返。

**`force-dynamic` 本身可以接受——问题在于没有配 `loading.tsx`**，
于是那段往返对用户是**完全不可见的空白**。两者必须配套。

## 4. 本次做什么 / 不做什么

### 做

| # | 改动 | 说明 |
| --- | --- | --- |
| a | **根 `src/app/loading.tsx`** | 覆盖所有未单独定义的页面。复用既有 `page-shell` / `page-header` / `content-section` 类，让骨架**接近**真实布局 |
| b | **给重页面加各自的 `loading.tsx`** | 首页（含记录网格）与列表页结构不同，各自一个 |
| c | **`app-shell.tsx` 的导航加 pending 态** | 用 Next 16 的 `useLinkStatus`：点击后立即标记「正在前往」，而不是等页面换掉 |

### **不做（关键边界）**

| 不做 | 原因 |
| --- | --- |
| **不改 `force-dynamic`** | 那会引入**数据陈旧风险**，需要逐页判断新鲜度要求——是另一个课题，不该混进来。**`loading.tsx` 不改变数据新鲜度**，这正是它性价比高的原因 |
| **不引入 Suspense 数据流式** | 需要重构页面取数方式，风险远大于收益 |
| **不造假内容** | 骨架只用中性色块，**不显示任何像是真实数据的文字**——避免用户误读 |

## 5. 验收（可判定）

| # | 标准 | 怎么验 |
| --- | --- | --- |
| 1 | 导航后**立刻**出现骨架，而不是空白 | 点击导航，肉眼可见骨架；或用 curl 看 HTML 里含骨架标记 |
| 2 | 骨架与真实布局**位置接近**，内容到达时**不明显跳变** | 对比骨架与真实页面的外层结构 |
| 3 | 样式复用既有类，**未新造一套设计语言** | 骨架使用 `page-shell` / `content-section` 等既有类 |
| 4 | 单测 / typecheck / lint / build 全过 | 既有门 |
| 5 | 无数据行为变化 | 各页面仍返回相同状态码与内容 |
