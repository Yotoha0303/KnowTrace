## 1. 实测：切换界面时现在是什么体验

**服务端本身不慢**【实测，登录后逐页测】：

**但用户感知由三件事决定，而它们全是缺的**【实测】：

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | **`loading.tsx` 数量 = 0** | 点击导航后**没有任何即时反馈**，界面要等新页面**完全渲染完**才切换 |
| 2 | **14 个页面里 10 个 `force-dynamic`** | 每次导航都必须回服务端完整渲染，拿不到缓存 |
| 3 | **导航无 pending 指示**（`useLinkStatus` / `isPending` / `Suspense` 全无） | 等待期间界面像"卡住"，诱导重复点击 |

**所以体感是**：点击 → 界面纹丝不动 → 等 0.06–0.33s → 整页换掉。**没有过渡、没有骨架、没有 loading。**

## 3. 根因

一个**结构性选择**：为"数据永远新鲜"，10 个页面选了 `force-dynamic`。
代价是每次切换都一次完整的服务端往返。

**`force-dynamic` 本身可以接受——问题在于没有配 `loading.tsx`**，
于是那段往返对用户是**完全不可见的空白**。两者必须配套。

---

## 4. 本次做什么 / 不做什么

### 做

| # | 改动 | 说明 |
| --- | --- | --- |
| a | **根 `src/app/loading.tsx`** | 覆盖所有未单独定义的页面。复用既有 `page-shell` / `page-header` / `content-section` 类，让骨架**接近**真实布局 |
| b | **给重页面加各自的 `loading.tsx`** | 首页（含记录网格）与列表页结构不同，各自一个 |
| c | **`app-shell.tsx` 的导航加 pending 态** | 用 Next 16 的 `useLinkStatus`：点击后立即标记「正在前往」，而不是等页面换掉 |

### **不做（关键边界）**

| 不做 | 原因 |
| --- | --- |
| **不改 `force-dynamic`** | 那会引入**数据陈旧风险**，需要逐页判断新鲜度要求——是另一个课题，不该混进来。**`loading.tsx` 不改变数据新鲜度**，这正是它性价比高的原因 |
| **不引入 Suspense 数据流式** | 需要重构页面取数方式，风险远大于收益 |
| **不造假内容** | 骨架只用中性色块，**不显示任何像是真实数据的文字**——避免用户误读 |

### 6.2 关键证据（Next 流式的表现）

```
$ curl -s http://127.0.0.1:3465/login | grep -o 'skeleton-block' | wc -l
24
$ ... | grep -o 'skeleton-card' | wc -l
12
$ ... | grep -o '登录 KnowTrace' | wc -l
1          ← 真实内容也在同一个响应里
```

**骨架与真实内容出现在同一个响应中**——这正是 Next 流式的预期：
**先送骨架（用户立刻看到），再送内容（渲染完成后替换）**。

无障碍文案也在（RSC 载荷里，所以直接 grep 属性名会漏）：

```text
"className":"sr-only","role":"status","children":"正在加载页面内容…"
```

### 6.3 与计划的差异

| 计划 | 实际 |
| --- | --- |
| 「导航链接加 pending 态」 | ✅ 但发现一个**易错点**：`useLinkStatus` 读的是**最近的 Link 祖先**的状态，必须在 Link 的**子组件**里调用。同组件内调用会拿到自己那层的上下文。因此把导航抽成 `sidebar-nav.tsx`，其中 `NavItemContent` 专门负责这项 |
| 计划外 | **抽出 `src/components/sidebar-nav.tsx`** —— `app-shell.tsx` 保持服务端组件，只把 `<nav>` 这一块移出，避免为一个 pending 态把大量服务端渲染搬到客户端 |
| 计划外 | `app-shell.tsx` 有六个图标（`Archive`/`ArrowLeftRight`/`ContactRound`/`Inbox`/`Scale`/`Search`）在迁移后**只剩 import**，已清理 |
| 计划外 | 需要新增 `.sr-only`（项目原先没有） |

### 6.4 我在验证中查错了一次（记录以免误导）

第一次验证时我 grep 了 `.next/app-path-routes-manifest.json` 与 `find .next/server/app -name "*loading*"`，
**都返回空**，一度判断「构建产物里没有 loading 模块」。

**那是查错了地方**：Next 16 的 Turbopack 把 loading 放在
`.next/server/chunks/ssr/src_app_loading_tsx_*.js`，与路由清单分开放。

第二次验证也有一次误判：未登录请求 `/` 与 `/claims` 返回 **307**，
**根本没渲染到页面** —— 我拿重定向的响应去 grep 骨架，自然为 0。
换成公开页 `/login` 才测到。

**两条都不是代码问题，是我查的位置不对**——记下来，因为「查不到」很容易被误读成「没生效」。
